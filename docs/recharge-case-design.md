# 回充失败单流程开发回归案例设计（v0）

## 0. 状态与边界

- 对应任务：P1-02 起步案例集（12–16 条），服务 P1-03「回充失败」单流程多轮售后状态开发。
- 本轮产物：16 条人工构造案例，全部在 `eval/cases/v0/recharge-start.json`。
- 数据集标识：`suite_id=recharge-start`、`split=development`、`source=synthetic-human-reviewed-pending`。
- 不是真实用户数据，不是正式留出集，不是统计样本。
- 16 条全部用于开发回归；不得把它们改标为 holdout，也不得用这 16 条宣称成功率、召回率、显著性或“真实用户验证”。
- 本轮没有运行模型、没有启动服务、没有读取或写入密钥；只做了 JSON 解析和来源片段存在性核对。
- 人工复核仍待完成；`source` 中的 `pending` 就是这个意思，不能省略。

## 1. 目的与非目标

### 1.1 目的

1. 给 P1-03 的状态开发提供可重复的开发验收输入：现象、已试步骤、用户更正、必要追问、来源作用域、下一步。
2. 覆盖直接回充询问、已试失败、否定未试、缺上下文、成功结案、主题切换、未知型号、域外问题、资料冲突、超时、会话恢复/隔离、重复请求和安全维修边界。
3. 让每条预期都能被人工复核，并尽量让“事实断言”停留在用户可见语义层，不绑定尚未定义的内部状态 schema。
4. 给后续 40–60 条案例的采样和留出划分留下可扩展结构。

### 1.2 非目标

- 不定义 runtime 的状态机、字段名、数据库表或 API。
- 不提供标准答案全文，不要求模型逐字匹配。
- 不评估模型的一般知识、闲聊能力或服装搭配能力。
- 不把检索命中当作答案正确；引用存在也不等于引用支持事实。
- 不用单次真实运行结果反推总体指标。
- 不在本轮实现评测入口、打分器或故障注入器。

## 2. 输入与证据

### 2.1 只读输入

- `assets/knowledge/` 六份资料：`故障排除.txt`、`扫地机器人100问.pdf`、`扫地机器人100问2.txt`、`扫拖一体机器人100问.txt`、`维护保养.txt`、`选购指南.txt`。
- 产品 `README.md`：知识库只含 6 份扫地/扫拖资料，不含服装资料；回答要求真实检索、来源引用、资料不足先追问。
- 现有检索/运行证据：
  - `my_agent_harness/outputs/robot-vacuum-restore/probe.json`：3 个检索查询的命中片段。
  - `my_agent_harness/outputs/robot-vacuum-restore/rag-verification.json`：检索片段与来源文件。
  - `my_agent_harness/outputs/robot-vacuum-restore/e2e-real-llm.json`：一次回充问答，19.38 秒、2586 tokens、列出 3 个来源；但 node scratch 同时记录了“回答缺少 [来源] 引用”，说明这次回答不能当作引用格式金标。
  - `my_agent_harness/outputs/robot-vacuum-restore/e2e-no-basis.json`：一次 Galaxy X99 无依据案例，17.3 秒、3641 tokens，未编造具体价格，`followup_detected=true`、`fabricated_specific_price=false`。
  - `my_agent_harness/outputs/robot-vacuum-restore/report.json`：823 条向量、6 份知识文件、上述两次端到端案例的汇总。

这些证据只用于说明“链路曾经跑通”和“哪些片段可检索到”，不证明覆盖率、正确率或稳定性。

### 2.2 来源片段规则

- `sources[].file` 使用相对本工程的路径，当前只为 `assets/knowledge/*` 和 `README.md`。
- `sources[].quote` 必须是原文中的真实片段，逐字摘录；不能改写、概括或拼接不存在的句子。
- PDF 片段用 `pdftotext -enc UTF-8 -layout` 提取后核对；换工具时需重新核对，提取差异不应被当成资料变更。
- 生成式回答、检索报告里的模型输出不作为事实来源；它们只出现在 `notes` 里作为运行证据。
- 资料之间冲突时保留双方原文，不替资料造统一值。当前明确冲突：`选购指南.txt` 第 36 条写“支持自动回充精准度≥95%”，第 84 条写“在复杂环境下回充精准度≥90%”。
- 危险维修只建议官方售后；不要把“外部擦拭触点”扩展成拆机、打磨内部触点或更换主板。

## 3. JSON 契约与字段解释

顶层：

```json
{
  "schema_version": 1,
  "suite_id": "recharge-start",
  "split": "development",
  "source": "synthetic-human-reviewed-pending",
  "description": "...",
  "cases": []
}
```

单条 case：

```json
{
  "id": "rs-01-direct-recharge",
  "title": "直接询问回充失败如何排查",
  "tags": ["direct", "single-turn", "retrieval", "citation", "auto-assisted"],
  "check_mode": "auto-assisted",
  "turns": [
    {
      "user": "...",
      "expect": {
        "facts": ["..."],
        "must_not": ["..."],
        "behavior": ["..."]
      }
    }
  ],
  "sources": [
    {"file": "assets/knowledge/故障排除.txt", "quote": "..."}
  ],
  "notes": "..."
}
```

字段语义：

| 字段 | 含义 | 实现适配说明 |
| --- | --- | --- |
| `id` | 稳定案例 ID | 追加案例时不要重编号；新案例用新 ID |
| `title` | 人读标题 | 不参与自动判定 |
| `tags` | 检索/分组标签 | 可用于筛选，不要求 runtime 识别 |
| `check_mode` | 验收方式 | `auto-assisted` / `human` / `fault-injection` / `integration` |
| `turns[].user` | 用户可见输入 | 不包含隐藏提示词；不要把它当真实用户原话引用 |
| `expect.facts` | 期望出现的用户可见语义断言 | 是行为/内容断言，不是内部字段名；实现可自行映射到状态 |
| `expect.must_not` | 禁止出现的内容或做法 | 优先用语义判断；部分可用禁用词/正则做预检 |
| `expect.behavior` | 过程性期望 | 如追问、更新状态、切主题、结案、幂等 |
| `sources` | 事实锚点 | 不是要求回答逐字复述；回答中的事实应能回到这些片段 |
| `notes` | 设计意图、证据、局限 | 不进入用户对话 |

可选扩展字段（只在需要的案例出现）：

- `setup`：会话恢复/跨 session 隔离的前置步骤，见 `rs-13`。
- `fault_injection`：故障注入类型与目标，见 `rs-12`。
- `turns[].session`：该轮属于哪个会话，见 `rs-13`。
- `turns[].request_id`：同一请求的重复提交标识，见 `rs-14`。

### 3.1 为什么不把 facts 写成内部 schema

P1-03 的最小状态字段是“现象/机型（可选）/已试步骤/来源作用域/下一步动作/未解决问题”，但当前 runtime 还没有稳定的状态 schema。若案例直接写 `phenomenon=...`，会把案例集和某个实现绑死，后续换存储或改字段就会制造假失败。

因此本集用三类语义断言表达：

- `facts`：用户应该看到什么、状态上应该承认什么；
- `behavior`：应该追问、更新、切换、结案还是拒答；
- `must_not`：不应该出现什么。

实现可以把它们映射到自己的状态字段；案例不规定字段名。

### 3.2 验收粒度

- `facts` 不要求逐字命中，允许同义表达；但不能改变事实方向。
- 数字、保修年限、阈值、文件名属于强约束，引用时必须与原文一致。
- `must_not` 中的安全类、编造类、跨域类要求应作为硬失败。
- `behavior` 允许合理措辞差异，但不能反向执行（例如用户已结案还继续要求拆机）。

## 5. 自动、人工、故障注入、集成有什么区别

### 5.1 自动辅助（`auto-assisted`）

这里的“自动”不是让模型当裁判，也不是宣称语义全自动。可以自动做的是确定性预检：

- JSON 能否解析；
- 必填字段是否存在、ID 是否唯一；
- `sources[].file` 是否存在，`quote` 是否能在原文中逐字找到；
- 回答是否出现明确禁止的字符串（如具体价格数字、拆机步骤关键词）；
- 是否引用了真实存在的来源文件名；
- 重复请求两次的用户可见文本是否几乎完全重复；
- 会话 A/B 的回复里是否出现对方的特有事实。

语义层的“说得对不对、是否过度回答、是否把冲突说成统一值”仍需人工判定。因此 `auto-assisted` 的最终结论是“自动预检 + 人工复核”，不能写成“自动通过”。

### 5.2 人工（`human`）

适用于语义/安全判断占主导的案例：

- 域外拒答是否自然、是否真的没有给服装建议；
- 冲突资料是否两边都呈现，是否偷偷选了一个数；
- 危险维修是否既拒绝拆机、又没有把外部清洁一起禁掉；
- 结案、更正、追问的语气是否合适。

建议两名复核者独立按同一 rubric 判定：通过 / 部分通过 / 失败；分歧记录理由并由第三人裁决。当前尚未进行双人复核，所以状态是 pending。

### 5.3 故障注入（`fault-injection`）

`rs-12` 不是自然用户输入，而是 harness 在网络层或工具层注入一次超时。它验证的是失败分支：

- 是否明确告诉用户“本次查询/生成未完成”；
- 是否把超时误说成“知识库没有资料”；
- 是否编造来源、结论或引用；
- 重试后是否恢复正常。

故障注入样本不得计入真实用户分布，也不得和自然案例混在一起算“用户问题解决率”。它需要单独的注入器和运行记录。

### 5.4 集成（`integration`）

`rs-13` 需要按 `setup` 建两个 session，再断线/恢复，属于集成验收：

- 同一 session 恢复后读取原状态；
- 新 session 不读取其他 session 的状态；
- 不把会话历史简单等同于结构化任务状态。

它不是单条消息能测的，也不应由模型“凭记忆”通过。当前 JSON 只描述步骤，不包含运行结果。

## 6. 关键设计决定

### 6.1 状态语义先于字段

案例只要求“记住已试/未试、更正后覆盖、结案后停止追问、切主题保留旧任务”，不要求某个字段名。这样 P1-03 可以先做规则/schema 的确定性部分，模型只负责追问、归纳和排序。

### 6.2 已试步骤要能“向前推进”

`rs-02`、`rs-03`、`rs-07`、`rs-08` 都在检查同一件事：不能把用户已经做过的步骤再当作首要建议，也不能把没做过的步骤记成做过。下一步应转向未验证的分支，例如充电座指示灯/供电、红外信号、手动放回测试。

### 6.3 缺上下文先追问

`rs-04` 故意只给“回充失败”“还是不行”。正确行为不是猜主板，也不是一次倾倒全部步骤，而是用一到两个关键问题补齐：什么现象、已试什么、充电座指示灯是否亮。

### 6.4 来源作用域

- 回充问题只引用回充/充电相关片段；
- 拖地不出水切到拖地片段，不拿回充传感器解释；
- 服装问题直接说明不在知识库范围；
- 未知型号不拿泛化选购价格区间冒充具体售价。

### 6.5 冲突与无依据

- 冲突：`选购指南.txt` 的 ≥95% 与 ≥90% 同时保留，明确说资料不一致，不替资料造统一标准。
- 无依据：Galaxy X99 没有型号资料，不能编价格；通用保修只能作为一般说明，并注明以说明书/发票/官方为准。
- 现有 `e2e-no-basis.json` 只验证一次，不能外推为“追问准确率”。

### 6.6 安全边界

`rs-15` 明确拒绝拆机、打磨内部触点、换主板的教学；`rs-06` 也拒绝自行拆水泵/内部管路。外部低风险清洁（干布擦拭触点、清理充电座周围）可以建议，但不能越界成内部维修。

### 6.7 会话与幂等

- 会话恢复：同一 session 断线重连后保留已试步骤。
- 跨 session 隔离：新 session 不能读到旧 session 的状态。
- 同 request 重复：不把一次请求计成两个新问题，不重复堆叠事实/来源；可以返回一致结论或简短说明沿用上次结果。

## 7. 后续 40–60 条案例的采样与留出建议

### 7.1 规模与划分

当前 16 条是起步开发集，不是留出集。建议：

| 总规模 | 开发集 | 留出集 | 说明 |
| --- | --- | --- | --- |
| 40（最低） | 24 | 16 | 保留当前 16 条在开发集，再补 8 条开发、16 条留出 |
| 48（建议） | 28 | 20 | 覆盖更完整的分层，仍不追求统计显著 |
| 60（上限） | 36 | 24 | 留出集不少于 20 条，避免太少导致结论飘忽 |

留出集单独文件、单独版本，不放进 `recharge-start.json`。建议未来路径（本轮不创建）：`eval/cases/v1/recharge-holdout.json`。

### 7.2 分层维度

按以下维度分层，不要只按“问法”随机凑数：

1. 意图：直接排查、已试失败、否定未试、模糊缺信息、成功结案、转主题、更正、回忆、未知型号、域外、冲突、超时、会话、重复、安全、错误前提。
2. 轮次：单轮 / 2 轮 / 3 轮以上。
3. 状态：无状态、已试步骤、未试、已解决、已暂停、已切换、已更正。
4. 来源：单文件、多文件、冲突文件、空检索、PDF/TXT 混合。
5. 失败类型：检索空、引用缺失、引用不支持、编造数字、跨域、重复、超时、状态丢失、跨 session 污染。
6. 安全：外部清洁、内部维修、电气/电池风险。

40 条时每层至少 2 条；60 条时关键层至少 3–4 条。不要为了凑数把同一模板换几个词，近重复会虚增样本量。

### 7.3 采样来源

- 资料驱动的合成边界：从六份资料中找真实冲突、空检索、型号缺失、危险操作边界。
- 失败驱动：每次开发运行后，把真实失败模式补成案例；失败案例比“再写一条正常问法”更有价值。
- 真实匿名日志：只有在取得授权、去除个人信息、确认可复查后才加入；当前没有真实用户数据，不能假装有。
- 对抗变体：短句、错别字、口语、指代（“它”“那个”）、话题突然切换；变体要单独计数，不能和原案例重复计入留出。

### 7.4 留出集隔离

- 留出集写好后冻结，记录文件 hash 和版本；开发过程中不读、不调 prompt、不按留出失败逐条改。
- 按用户/session 或“同义改写簇”划分，不要随机切近重复；否则留出会泄漏。
- 开发集和留出集不得有同一 source quote + 同一预期行为的近重复。
- 留出集只用于阶段性评估；不能拿 16 条起步集冒充留出，也不能拿 40–60 条宣称统计显著。

### 7.5 复核与指标

- 指标按可实测范围：答案支持度、引用是否真实且支持、缺依据追问、多轮一致、任务完成、延迟 p50/p95、token/费用；工具调用成功与任务完成分开。
- model judge 只能做辅助，必须注明局限；规则/人工为主。
- 40–60 条只用于发现明显退化，不宣称统计显著；报告写清 N、版本、采样方式和未覆盖项。

## 10. 变更规则

5. 任何从开发集转留出的动作都必须新建文件、记录版本和 hash；不能直接改 `split` 字段冒充留出。
6. 人工复核完成后，才把 `source` 从 `synthetic-human-reviewed-pending` 改为已复核状态；不能用“人工构造”冒充“人工复核通过”。
